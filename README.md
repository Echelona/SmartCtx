พัฒนาโดย CatCode Studio

## เริ่มต้นใช้งาน

```bash
npm install
npm start
```

## แก้บั๊ก: ลงรับของที่ยังไม่ได้จัดส่งจริง

**ปัญหาเดิม:** ตอนลงรับเข้าคลัง ระบบตรวจสอบยอดเทียบกับ "จำนวนที่เบิกไปทั้งหมด" (qty_requested)
ไม่ใช่ "จำนวนที่จัดส่งมาจริง" (qty_shipped) — ทำให้รายการที่ยังค้างส่งอยู่ที่งานจัดซื้อ (ยังไม่ส่งเลย
หรือส่งมาไม่ครบ) สามารถถูกลงรับเข้าคลังได้เหมือนของมาถึงแล้วจริงๆ

**แก้แล้วทั้งสองชั้น:**
- **Backend (จุดที่บังคับจริง)** — `stock.db.js` ตอนนี้ตรวจสอบยอดรับเข้าเทียบกับ `qty_shipped - qty_received`
  เท่านั้น ถ้าพยายามลงรับเกินกว่าที่จัดส่งมาจริง ระบบจะปฏิเสธทั้งคำขอ (400) พร้อมบอกจำนวนที่รับได้จริง
  และ rollback ธุรกรรมทั้งหมด (ไม่มี stock ใดๆ ถูกสร้างจากคำขอที่ถูกปฏิเสธ) — ยานอกใบเบิก (ไม่ตรงกับ
  รายการที่เบิกไว้เลย) ยังคงรับแบบ ad-hoc ได้ตามปกติ ไม่ถูกจำกัดเกินจำเป็น
- **Frontend** — ตอนเลือกใบเบิกอ้างอิงในฟอร์มรับเข้า ตะกร้าจะเติมให้เฉพาะรายการที่ "จัดส่งมาแล้วจริง"
  เท่านั้น ถ้ามีรายการที่ยังค้างส่งอยู่ที่งานจัดซื้อ จะไม่ถูกเติมให้ และมีข้อความแจ้งให้รู้ว่ายังมีรายการ
  ค้างส่งอยู่กี่รายการ

**ทดสอบแล้ว 9 สถานการณ์ผ่าน HTTP จริง:** ปฏิเสธการรับก่อนส่ง, ปฏิเสธการรับเกินยอดส่งจริง (พร้อม
ยืนยันว่า rollback ไม่ทิ้ง stock ค้าง), รับได้พอดีตามยอดที่ส่งจริง, ปฏิเสธการรับซ้ำโดยไม่มีส่งเพิ่ม,
ส่งส่วนที่เหลือแล้วรับจนครบสถานะเปลี่ยนเป็น "received" ถูกต้อง, ยานอกใบเบิกยังรับได้ปกติ

## ตรวจสอบวันผลิต/วันหมดอายุตอนรับเข้าคลัง

ตรวจสอบทั้งฝั่ง frontend (แจ้งเตือนทันที) และ **backend** (บังคับจริง ปฏิเสธคำขอถ้าไม่ผ่าน):
- วันผลิตห้ามเป็นวันที่ในอนาคต
- วันหมดอายุห้ามเป็นวันที่ผ่านมาแล้ว (ของหมดอายุไม่สามารถรับเข้าคลังใช้งานได้)
- วันหมดอายุต้องอยู่หลังวันผลิตเสมอ (ถ้ากรอกทั้งสองค่า)
- ไม่บังคับต้องกรอกทั้งสองวัน — ถ้าไม่กรอกเลยก็ยังรับเข้าได้ปกติ (ตรวจเฉพาะเมื่อมีค่า)

ปฏิเสธทั้งใบถ้ามีรายการใดรายการหนึ่งไม่ผ่าน (ไม่ใช่แค่ข้ามรายการนั้นเงียบๆ) ทดสอบผ่านทั้ง 4 กรณี
(EXP ในอดีต, MFG ในอนาคต, EXP≤MFG แม้ทั้งคู่เป็นวันที่ปัจจุบันที่ผ่านกฎอื่นแล้ว, วันที่ถูกต้องปกติ) รวมถึง
กรณีไม่กรอกวันที่เลยยังทำงานได้ปกติ

## แก้บั๊ก: sqlite error ตอนแก้ไขรายการยาแล้วบันทึก (คอลัมน์ไม่มีอยู่จริงในฐานข้อมูลเดิม)

**สาเหตุจริง:** ไม่ใช่ตัวสะกดผิดในโค้ด (เช็คแล้วไม่มี) — แต่เป็นเพราะ `CREATE TABLE IF NOT EXISTS` ที่ใช้
สร้าง schema **ไม่เพิ่มคอลัมน์ใหม่ให้ตารางที่มีอยู่แล้ว** ถ้าเคยรันแอปนี้มาก่อนตอนที่ยังไม่มีคอลัมน์
`strength_value`/`pack_size_value` (เพิ่มเข้ามาทีหลังในการพัฒนาสองรอบล่าสุด) ไฟล์ฐานข้อมูลเดิมจะขาด
คอลัมน์เหล่านี้ไปเลย พอโค้ดพยายาม UPDATE/INSERT คอลัมน์ที่ไม่มีอยู่จริงในตาราง ก็เกิด SQLite error

**แก้แล้ว:** เพิ่มระบบ migration อัตโนมัติใน `warehouseSchema.db.js` — ทุกครั้งที่ server เริ่มทำงาน จะเช็ค
ทุกตารางว่ามีคอลัมน์ที่ควรจะมีครบไหม (ผ่าน `PRAGMA table_info`) ถ้าขาดคอลัมน์ไหนจะรัน `ALTER TABLE ...
ADD COLUMN` เติมให้อัตโนมัติ โดยไม่กระทบข้อมูลเดิมที่มีอยู่แล้วเลย (แค่เติมคอลัมน์ว่างเข้าไป ไม่ลบ/ไม่แก้
ข้อมูลแถวเดิม) — ครอบคลุมทั้ง `drug_master`, `requisition_items`, `receipt_items`, `stock_lots`

**ทดสอบด้วยการจำลองสถานการณ์จริง ไม่ใช่แค่เขียนโค้ดแล้วเดา:** สร้างฐานข้อมูลด้วย schema แบบเก่า
(ตัดคอลัมน์ที่เพิ่งเพิ่มออกโดยตั้งใจ) ใส่ข้อมูลยาตัวอย่างเข้าไป แล้วเปิด server ชี้ไปที่ฐานข้อมูลนั้น —
ยืนยันว่า migration รันอัตโนมัติ 16 รายการ ข้อมูลเดิมไม่หาย แล้ว**ทำซ้ำสถานการณ์ที่รายงานบั๊กเป๊ะๆ**
(แก้ไขยาตัวนั้นแล้วกดบันทึก) ยืนยันว่าสำเร็จ (200 OK) แทนที่จะพังแบบเดิม พร้อมทดสอบคู่ขนานว่าฐานข้อมูล
ใหม่ที่สร้างสดๆ ไม่มีการรัน migration ที่ไม่จำเป็น (ไม่กระทบ performance การเริ่มระบบปกติ)

ไฟล์ zip นี้จึงใช้ทับของเดิมได้เลยไม่ว่าฐานข้อมูลจะอยู่ในสถานะไหนมาก่อน ไม่ต้องลบ `data/*.db` แล้วเริ่มใหม่

## ขนาดบรรจุ — แยกเป็นตัวเลข+หน่วยเช่นเดียวกับความแรง

ใช้แนวทางเดียวกับความแรงเป๊ะ: เพิ่มคอลัมน์ `pack_size_value` (ตัวเลข) + `pack_size_unit` (หน่วย) แยกจาก
`pack_size` (ข้อความแสดงผลเดิม เช่น "50 mL/vial") ในทุกตารางที่เกี่ยวข้อง (`drug_master`,
`requisition_items`, `receipt_items`, `stock_lots`) ไหลตามเอกสารไปตลอดสายเหมือนความแรง

- ยารูปแบบของเหลว (31 จาก 45 รายการอ้างอิง) แยกค่าตัวเลข+หน่วยให้ครบ
- ยารูปแบบผงแห้ง (14 รายการ) ไม่มีปริมาตรของเหลวจริง จึงปล่อยว่างไว้ถูกต้อง ไม่ใส่ค่าผิดๆ
- Drug Master form: "ขนาดบรรจุ" แยกเป็นช่องตัวเลข + dropdown หน่วย (มีตัวอย่างข้อความที่จะแสดงให้ดูสด)
  เหมือนช่องความแรง
- dropdown หน่วยขนาดบรรจุเป็นรายการใหม่ (`pack_size_unit`) แทนที่ dropdown เดิมที่เก็บข้อความรวม
  ("50 mL/vial" ทั้งก้อน) ซึ่งใช้การไม่ได้แล้วเมื่อแยกฟิลด์ — seed เริ่มต้นด้วย "mL"

**ตอนนี้ทั้งความแรงและขนาดบรรจุเป็นตัวเลขจริงพร้อมกันแล้ว** เปิดทางให้คำนวณความเข้มข้นได้ตรงๆ
(เช่น ยา 50mg บรรจุใน 50mL = ความเข้มข้น 1 mg/mL) โดยไม่ต้อง parse ข้อความทั้งสองค่าด้วย regex เลย

ทดสอบผ่าน HTTP จริง 6 ขั้นตอน ครบทั้งสาย: seed data (ทั้งกรณีของเหลวและผงแห้ง) → สร้างยาผ่าน dropdown
ใหม่ → ใบเบิก → จัดส่ง+รับเข้า → ยืนยันค่าที่ stock_lots → **คำนวณความเข้มข้นจริง** (50mg/50mL = 1 mg/mL
ถูกต้อง) → ยืนยัน stock-summary ก็มีข้อมูลครบสำหรับหน้าจอสรุปด้วย

## รายการยา — ช่องหน่วย/ขนาดบรรจุ/หน่วยความแรง/หมวดหมู่ เป็น dropdown แก้ไข/เพิ่มได้ภายหลัง

เดิมทั้ง 4 ช่องนี้เป็นข้อความอิสระ (พิมพ์เองได้ตามใจ) เปลี่ยนเป็น dropdown ที่ดึงจากรายการตัวเลือกกลาง
(`lookup_options`) — เลือกจากของเดิมได้ทันที และมี "+ เพิ่มตัวเลือกใหม่..." ท้าย dropdown ทุกอัน กด
แล้วพิมพ์ค่าใหม่ ระบบบันทึกและเลือกให้ทันทีโดยไม่ต้องออกจากฟอร์ม

ปุ่ม "⚙️ จัดการตัวเลือก" ในแท็บรายการยา เปิดแผงจัดการแยกตามประเภท (หน่วย/ขนาดบรรจุ/หน่วยความแรง/หมวดหมู่)
แก้ไขชื่อหรือปิดใช้งานตัวเลือกเดิมได้ — ปิดใช้งานแบบ soft-delete (ไม่ลบจริง) ยาที่เคยใช้ค่านั้นอยู่แล้ว
ไม่กระทบ แค่ตัวเลือกนั้นจะไม่โผล่ให้เลือกใหม่อีก

ค่าเริ่มต้น seed จากรายการยาอ้างอิง 45 รายการ (หน่วยความแรง 7 แบบ, ขนาดบรรจุ 13 แบบ, หมวดหมู่ 2 แบบ) —
seed แค่ตอนตารางว่างเปล่าเท่านั้น เหมือนแนวทาง Drug Master

ทุกการเปลี่ยนแปลงตัวเลือก (เพิ่ม/แก้ไข/ปิดใช้งาน) กระจาย real-time ผ่าน event `lookup:changed` ไปยัง
หน้าจออื่นทันที — ทดสอบผ่าน HTTP + socket.io จริง 6 สถานการณ์ครบ (เลือกจาก dropdown, เพิ่มใหม่แบบ inline,
กระจาย real-time ข้ามหน้าจอ, rename, ปิดใช้งานแล้วไม่กระทบข้อมูลเดิม)

**บั๊กที่เจอระหว่างทดสอบและแก้แล้ว:** ฟังก์ชัน seed ของ Drug Master กับของตัวเลือก dropdown เดิมเรียกแยกกัน
แบบไม่รอกัน (unawaited) ทำให้ทั้งสองพยายามเปิด transaction พร้อมกันแล้วชนกัน (`cannot start a transaction
within a transaction`) — แก้โดยให้ seed เรียงลำดับกันเสมอ

## ช่องความแรง — แยกเป็นตัวเลข+หน่วย รองรับคำนวณจริง

เดิม "ความแรง" เป็นข้อความล้วน เช่น `"50 mg"` — ใช้แสดงผลได้ แต่ถ้าจะเอาไปคำนวณ (เช่น ต้องการยา 120mg
ใช้กี่ขวด) ต้อง parse string ด้วย regex ทุกครั้ง เสี่ยงพังถ้ารูปแบบไม่ตรงเป๊ะ

**แก้แล้ว:** เพิ่มคอลัมน์ `strength_value` (ตัวเลข) และ `strength_unit` (หน่วย) แยกต่างหาก ในทุกตารางที่เกี่ยวข้อง
(`drug_master`, `requisition_items`, `receipt_items`, `stock_lots`) — ข้อความแสดงผล `strength` (เช่น "50 mg")
ยังคงอยู่เหมือนเดิมเพื่อความเข้ากันได้กับหน้าจอที่มีอยู่แล้ว แต่ตอนนี้มีค่าตัวเลขจริงให้ดึงไปคำนวณได้ตรงๆ
ไม่ต้อง parse ข้อความอีกต่อไป

- แก้ไข/เพิ่มยาใน Drug Master ตอนนี้กรอกเป็นตัวเลข + หน่วยแยกกัน 2 ช่อง (มีตัวอย่างข้อความที่จะแสดงให้ดูสด)
- ค่าตัวเลขนี้ไหลตามเอกสารไปตลอด: สร้างยาใน Drug Master → เพิ่มเข้าใบเบิก → จัดส่ง → รับเข้าคลัง → กลายเป็น
  ส่วนหนึ่งของ **stock_lots** (ระดับ Lot จริงที่ใช้งานได้) ซึ่งเป็นจุดที่โมดูลเตรียมยาเฉพาะรายในอนาคตจะ
  ดึงไปคำนวณได้โดยตรง (เช่น จำนวนขวดที่ต้องใช้ = ขนาดยาที่ต้องการ ÷ strength_value ของ Lot นั้น)
- ข้อมูลอ้างอิงยาเริ่มต้นทั้ง 45 รายการถูกแปลงเป็นค่าตัวเลข+หน่วยแยกให้เรียบร้อยแล้ว (รวมถึงกรณีทศนิยม
  เช่น "2.5 g" และหน่วยพิเศษอย่าง "unit")

ทดสอบผ่าน HTTP จริง 7 ขั้นตอนครบทั้งสาย ตั้งแต่ seed data → สร้าง/แก้ไขยาผ่านฟอร์ม → สร้างใบเบิก →
จัดส่ง+รับเข้า → ยืนยันค่าที่ stock_lots → **จำลองการคำนวณจริง** (ต้องการยา 120mg จาก Lot ที่มี 50mg/ขวด
คำนวณได้ 3 ขวดถูกต้องจากตัวเลขจริง ไม่ใช่ string parsing)

## คลังคงเหลือแยกตาม Lot + มูลค่าต้นทุนรวม

แท็บ "📦 คลังคงเหลือ" คลิกชื่อยาแต่ละแถวเพื่อขยายดูรายละเอียดแยกตาม Lot ได้แล้ว — Lot No., วันผลิต,
วันหมดอายุ, จำนวนรับเข้าสะสม, จำนวนคงเหลือ, ต้นทุนต่อหน่วย, มูลค่ารวมต่อ Lot, สถานะ (ใช้งานได้/หมดล็อต/หมดอายุ)
พร้อมแถวสรุปรวมจำนวน Lot + มูลค่ารวมของยาชนิดนั้นท้ายตาราง

เพิ่ม KPI "💰 มูลค่าคงคลังรวม" ที่หัวหน้า — รวมมูลค่าของทุกชนิดยาทั้งคลัง

ทดสอบผ่าน HTTP จริง: รับเข้ายาชนิดเดียวกัน 2 Lot คนละต้นทุน ยืนยันว่าตัวเลขที่ระดับ Lot, ระดับสรุปต่อยา,
และ KPI รวมทั้งคลัง คำนวณตรงกันทุกชั้น (ทดสอบด้วยยา 3 ชนิดพร้อมกัน มูลค่ารวม 44,000 บาท คำนวณถูกต้อง)

## แก้บั๊ก: เลือกใบเบิกค้างรับซ้ำแล้วรายการเพิ่มซ้ำสะสม

**ปัญหาเดิม:** ตอนเลือกใบเบิกอ้างอิงในฟอร์มรับเข้าคลัง ระบบเติมรายการยาลงตะกร้าด้วยการ "เพิ่มต่อท้าย"
เสมอ — ถ้าเลือกใบเบิกเดิมซ้ำ (เผลอเลือกซ้ำ หรือกลับมาเลือกใหม่เพราะมีการจัดส่งเพิ่ม) รายการจากใบเบิกนั้น
จะถูกเติมซ้ำสะสมตามจำนวนครั้งที่เลือก (เลือก 3 ครั้ง = ได้ยาซ้ำ 3 ชุด)

**แก้แล้ว:** ตอนนี้แต่ละรายการในตะกร้าจะจำไว้ว่ามาจากใบเบิกใบไหน (หรือเพิ่มเองด้วยมือ) — เลือกใบเบิกใบเดิมซ้ำ
จะ "แทนที่" รายการเดิมจากใบเบิกนั้นด้วยชุดใหม่ (มีประโยชน์เผื่อมีการจัดส่งเพิ่มระหว่างนั้นด้วย) ไม่ใช่เพิ่มต่อท้าย
รายการที่เพิ่มเองด้วยมือหรือมาจากใบเบิกอื่นไม่ถูกแตะต้อง เลือกได้หลายใบเบิกพร้อมกันในตะกร้าเดียวตามปกติ

ทดสอบด้วย unit test 6 สถานการณ์ครอบคลุมกรณีที่รายงานและกรณีข้างเคียง (เลือกซ้ำหลายรอบ, มี manual item ปน,
เลือกหลายใบเบิกพร้อมกัน, เลือกใบเบิกอื่นซ้ำไม่กระทบใบเบิกที่เลือกไว้ก่อน) — ผ่านทุกจุด

## ชื่อผู้รับ (ใบรับเข้าคลัง) และหน้าเลือกโมดูลเวอร์ชันใหม่

ฟอร์มรับเข้าคลังตอนนี้บังคับกรอก "ชื่อผู้รับ" เช่นเดียวกับ ชื่อผู้เบิก (ใบเบิก) และ ชื่อผู้ส่ง (การจัดส่ง)
— ทั้ง frontend (แจ้งเตือน+โฟกัสถ้าไม่กรอก) และ backend (ปฏิเสธด้วย 400 ถ้าไม่มีชื่อ) ไม่มี fallback
ไปใช้ username ที่ login อีกต่อไป ทดสอบผ่าน HTTP จริงทั้งกรณีปฏิเสธและกรณีบันทึกถูกต้อง

หน้าเลือกโมดูล (`core/public/index.html`) ใช้เวอร์ชันที่ปรับแก้เนื้อหาแล้วเป็นต้นแบบมาตรฐาน —
ป้ายกำกับโมดูล 2/3 เปลี่ยนจาก "โมดูล 2"/"โมดูล 3" เป็นชื่อบอกหน้าที่ตรงๆ ("โมดูลงานผลิต" /
"โมดูลงานดูแลผู้ป่วย") และปรับข้อความ footnote ให้กระชับขึ้น

## Danger Zone: ล้างข้อมูลทดสอบ

แท็บ "🧹 ข้อมูลทดสอบ" ในหน้างานคลังเคมีบำบัด — ใช้เฉพาะช่วงทดสอบระบบก่อนใช้งานจริงเท่านั้น

- ลบใบเบิก/การจัดส่ง/การรับเข้าคลัง/สต๊อกคงเหลือ/ประวัติความเคลื่อนไหว/การปรับปรุงยอดทั้งหมดถาวร
  **ไม่แตะรายการยา (Drug Master)** เพราะเป็นข้อมูลตั้งค่าระบบ ไม่ใช่ข้อมูลทดสอบ
- รีเซ็ตเลขที่เอกสาร (REQ/SHP/RCV) กลับไปเริ่มที่ 001 ใหม่ (auto-increment reset) แล้ว VACUUM ฐานข้อมูลให้สะอาด
- ต้องใช้รหัสผ่านแยกต่างหากจาก login ปกติ — ตั้งไว้ที่ `SUDO_CLEAR_PASSWORD` ใน `.env` (ค่าเริ่มต้น `sudo5889`
  ตามที่ระบุ — **ควรเปลี่ยนหรือลบฟีเจอร์นี้ก่อน deploy ใช้งานจริง**)
- มี double-confirmation: ต้องกรอกรหัสผ่าน + กด "ตกลง" ใน dialog ยืนยันอีกชั้น
- เมื่อล้างสำเร็จ ทั้งฝั่งจัดซื้อและคลังเห็นการเปลี่ยนแปลงทันทีผ่าน real-time event (`data:cleared`)
  ไม่ต้องรีโหลดหน้าเอง

ทดสอบผ่าน HTTP จริง 13 สถานการณ์: รหัสผ่านผิดถูกปฏิเสธ (403) และไม่ลบอะไรเลย, รหัสผ่านถูกต้องลบสำเร็จ,
drug_master ไม่ถูกแตะต้อง, ตัวเลขเอกสารรีเซ็ตกลับไปเริ่มที่ 001 จริง, event กระจายไปอีกฝั่งจริงผ่าน socket

## ฟีเจอร์ที่เพิ่มล่าสุด

**Real-time (ทุกโมดูล)**
- ใช้ Socket.IO แบบเดียวกับ `admin.js` (SmartPharmacy) — เมื่อฝั่งจัดซื้อกดจัดส่ง หรือฝั่งคลังสร้างใบเบิก/รับเข้า/แก้ไขรายการยา
  อีกฝั่งจะเห็นการเปลี่ยนแปลงทันทีโดยไม่ต้องรีโหลดหน้าเอง (มี fallback poll ทุก 60 วิ เผื่อ socket หลุดชั่วคราว)
- event ที่ส่ง: `requisition:created`, `shipment:created`, `receipt:created`, `drug:changed` — ส่งแค่ id/เลขที่เอกสาร
  ไม่ส่งข้อมูลเต็ม ฝั่งรับต้อง fetch ผ่าน REST API ที่มี auth ตามปกติ จึงไม่มีความเสี่ยงข้อมูลรั่วข้ามโมดูลผ่าน socket
- ทดสอบแล้วด้วย socket.io-client จริง (ไม่ใช่แค่เขียนโค้ดแล้วเดา) — เปิด connection คู่ขนาน สร้าง/แก้ไขข้อมูลจริง
  แล้ววัดว่า event มาถึงอีกฝั่งจริง พร้อม payload ตรงตามที่คาด

**การกรอกรายการยา — เปลี่ยนเป็นแบบ "ตะกร้า"**
- ทั้งฟอร์มสร้างใบเบิกและฟอร์มรับเข้าคลัง: เลือกยา + กรอกจำนวน (รับเข้าเพิ่ม Lot/วันที่/ราคา) แล้วกด "+ เพิ่มลงตะกร้า"
  รายการจะไปอยู่ในตารางตะกร้าด้านล่าง ลบออกทีละรายการได้ กด "บันทึก" ครั้งเดียวส่งทั้งตะกร้า
- ตอนเลือกใบเบิกอ้างอิงในฟอร์มรับเข้า ระบบเติมยาที่ยังค้างรับลงตะกร้าให้อัตโนมัติ (Lot No./วันที่ยังว่างให้กรอกเอง
  เพราะเป็นข้อมูลของจริงที่รู้ได้ตอนได้รับของจริงเท่านั้น) — แก้ไขได้ตรงในตารางตะกร้าเลยไม่ต้องลบแล้วเพิ่มใหม่

**ชื่อผู้เบิก/ผู้ส่ง — บังคับกรอกจริง**
- เดิมเป็นช่องกรอกที่ไม่กรอกก็ได้ (fallback ไปใช้ username ที่ login แทน) ตอนนี้บังคับกรอกทั้งฝั่ง frontend
  (แจ้งเตือน+โฟกัสช่องถ้าไม่กรอก) และฝั่ง backend (ปฏิเสธคำขอด้วย 400 ถ้าไม่มีชื่อ) — ไม่มี fallback ไปใช้ username อีกต่อไป

## สิ่งที่ทดสอบแล้วจริง (ไม่ใช่แค่เขียนแล้วเดาว่าถูก)

รันเซิร์ฟเวอร์จริงและยิง HTTP request ทดสอบ flow เต็มรูปแบบ:
- สร้างใบเบิกที่ 1.2 → 1.1 เห็นและจัดส่งบางส่วนได้ → 1.2 รับเข้าไม่ครบ → ระบบคำนวณยอดค้างจ่ายถูกต้อง
- กันจัดส่งเกินยอดคงเหลือ (validation reject)
- Login แยกแต่ละโมดูลจริง — session ของโมดูลหนึ่งเข้าโมดูลอื่นไม่ได้ (ทดสอบแล้วว่า 401)
- หน้าเว็บที่ยังไม่ login ถูก redirect ไป login page ของโมดูลนั้นถูกต้อง
- Static asset (CSS/JS/ข้อมูลอ้างอิงยา) โหลดผ่าน route ที่ถูก gate ด้วย auth ได้ปกติ
- รายการยา (Drug Master): seed อัตโนมัติครั้งแรก (45 รายการ), เพิ่ม/แก้ไข/ปิดใช้งานได้, กันรหัสยาซ้ำ (409),
  ปิดใช้งานแล้วไม่โผล่ในตัวเลือกใหม่แต่ประวัติเก่ายังอยู่ครบ — ทดสอบผ่านทุกจุด
- Real-time: เปิด socket จริง 2 ฝั่งพร้อมกัน สร้างใบเบิก/จัดส่ง/รับเข้า/แก้ไขยา แล้ววัดว่า event มาถึงจริงตรงเวลา
  พร้อม payload ถูกต้อง — ผ่านทั้ง 4 event type
- บังคับกรอกชื่อผู้เบิก/ผู้ส่ง: ทดสอบว่าคำขอที่ไม่มีชื่อถูกปฏิเสธด้วย 400 จริงทั้งสองฝั่ง (ไม่ใช่แค่ frontend validation)

## รายการยา (Drug Master)

อยู่ในแท็บ "💊 รายการยา" ของโมดูล 1.2 — เพิ่ม/แก้ไข/ปิดใช้งานยาได้เอง (ไม่ใช่ list ตายตัวในโค้ด)
ตามแนวทางเดียวกับ `admin.js` ที่แนบมา (ฟอร์ม add/edit เปิด-ปิดด้วย class, ปุ่ม Edit ดึงข้อมูลผ่าน
data-map แทนการฝัง JSON ใน onclick เพื่อกัน XSS) แต่ละรายการมี 3 ฟิลด์แยกกันตามที่ต้องการ:
**ชื่อยา (item) / ความแรง (strength) / ขนาดบรรจุ (pack size)** — ใช้คำนวณแยกกันได้ในโมดูลเตรียมยาต่อไป

ครั้งแรกที่รัน ระบบจะ seed รายการยาเคมีบำบัดที่ใช้บ่อยในไทย 45 รายการให้อัตโนมัติจาก
`shared-data/chemoDrugs.data.js` (seed แค่ตอนตารางว่างเปล่าเท่านั้น แก้ไขแล้วจะไม่ถูกทับ)
**ควรตรวจสอบ/ปรับให้ตรงกับบัญชียาจริงของโรงพยาบาลก่อนใช้งานจริง** — ไม่ใช่คำแนะนำทางการแพทย์

การลบเป็นแบบปิดใช้งาน (soft-delete) ไม่ใช่ลบทิ้งจริง เพราะใบเบิก/ใบรับเข้าเก่าเก็บชื่อ/ความแรง
ณ ตอนนั้นแยกไว้ในตัวเองอยู่แล้ว (denormalized) การซ่อนจาก dropdown ตัวเลือกใหม่จึงปลอดภัยกว่า

## สถาปัตยกรรม

```
SmartCtx/
├── server.js              จุดเริ่มต้น — ผูกทุกโมดูลเข้าด้วยกัน คนละ path namespace (/modules/<key>/...)
├── .env.example            รายการตัวแปรที่ต้องตั้งค่า (login แต่ละโมดูลอยู่ที่นี่ ตามสเปก)
├── data/                    ไฟล์ฐานข้อมูล SQLite (สร้างอัตโนมัติตอนรันครั้งแรก)
├── core/                    ใช้ร่วมกันทุกโมดูล — ธีมสี, session-timeout widget, ปฏิทินไทย, หน้าเลือกโมดูล
├── shared-data/             ข้อมูลอ้างอิงยาเคมีบำบัด (item/ความแรง/ขนาดบรรจุ แยกฟิลด์)
├── modules/
│   ├── _shared/backend/     schema ฐานข้อมูลกลางที่ 1.1 กับ 1.2 ใช้ร่วมกัน (requisitions/shipments/receipts/lots)
│   ├── procurement/         โมดูล 1.1 — backend + frontend ของตัวเอง
│   ├── stock-management/    โมดูล 1.2 — backend + frontend ของตัวเอง
│   ├── chemo-prep/          โมดูล 2 — เฉพาะ login + placeholder
│   └── pharm-care-unit/     โมดูล 3 — เฉพาะ login + placeholder
```

**แต่ละโมดูล login แยกกันจริง** ผ่าน `core/middleware/moduleAuth.middleware.js` — เช็ค username/password
จาก `.env` โดยตรง ไม่มีตารางผู้ใช้ในฐานข้อมูล login สำเร็จแล้วยังใช้ข้าม module อื่นไม่ได้
(session เก็บสถานะ login แยกเป็นรายโมดูล)

**Session timeout**: idle ครบ 4.5 นาทีจะเด้ง popup นับถอยหลัง 30 วิ ถ้าไม่กดต่ออายุ จะ logout
อัตโนมัติเมื่อครบ 5 นาที (`core/public/js/shared/sessionTimeout.shared.js`)

**วันที่ทั้งระบบแสดงแบบ dd/mm/yyyy พ.ศ.** ผ่านปฏิทินกำหนดเอง (`core/public/js/shared/thaiDate.shared.js`)
ค่าที่เก็บจริง/ส่งให้ backend ยังเป็น ISO ค.ศ. เหมือนเดิมทุกจุด
